# Actual Windows Code Remote WSL native preview proof

`summary.json` and `actual/full-smoke.json` record a passing real Windows Code 1.145.0 / stock Remote WSL 1.104.7 window. The actual workspace extension host reported `remoteName=wsl`, Linux x64, PID 816447; the Windows resolver extension host was PID 23836. The kernel inventory confirms Microsoft WSL2. This uses the exact final native-only VSIX SHA `d0cafff141d2ca5e318a0bc0633150f2ce896e356a399bea92b44dec7ba35eb6` and actual static Linux amd64 native preview `native-preview-20261110-cd6b769ebe6e`, SHA `eecbbc71e3c5a2234302fd637d5d668fc641935b32e878124f1b628a59473380`. It is one actual editor workflow window, rather than the earlier component-model tests or a multiple-window WSL proof.

The real packaged extension used its native launch path against a private native controller and standalone Docker worker inside WSL. The test asserted capture from a workspace path containing spaces, live Docker command/log output, an exact 2,048-byte artifact tar and its exact contents, one JUnit case through the real VS Code Testing integration, and cancellation after a long job reached running. Missing and incompatible native helpers produced the expected discovery errors, all launch items became error items, no TypeScript fallback occurred and no additional jobs were submitted. Restoring the verified helper restored discovery.

Before Gridstator activation, the full launcher verified the native executable hash/build ID/target, VSIX hash and extracted bytes, exact private config/URL/CA, controller port/runtime PID/executable and authenticated expected cluster ID. Runtime actions repeated the private config/cluster/client checks. The default controller port was refused.

`window_guard.py` and `launch_guarded.py` were reviewed before the successful launch. They require private client user/extensions/shared/agent/download/crash directories, in-memory secret storage, exact private remote/test URIs, sanitized process-only environment and a free stock resolver-pipe namespace. Pure missing-path negatives and a real uniquely owned Windows named-pipe fixture proved rejection before Code launch. The stock Windows executable and all Remote WSL plugin bytes were preserved. The private client product JSON changes only `serverDataFolderName`; the private downloaded server product changes only `serverDataFolderName` and `sharedDataFolderName`. `VSCODE_AGENT_FOLDER` and `VSCODE_PORTABLE` also point inside the private prefix. Effective Machine settings live under `server/portable/user-data/Machine`; a first full attempt caught and corrected the harness's earlier unused settings location. These metadata/configuration changes are explicitly test isolation, not an unmodified default editor setup. No Gridstator production source changed.

An early empty-window diagnostic opened the preexisting Windows shared-storage database despite a private user-data directory. It reported `wasCreated: false`; zero writes are not guaranteed. The database was not reset. No Windows Gridstator extension/backend/action was involved in that diagnostic, and the exact original 23 desktop PIDs and legacy service unit remained unchanged. See `diagnostic-README.md` and `windows-diagnostic-isolation.json`. Subsequent guarded windows used in-memory shared storage, as captured in `actual/actual-host-and-storage.json`. Failed direct-launch and effective-Machine-location preflights are retained rather than relabelled as successes.

`cleanup.json` verifies private native actors exited, own labelled Docker containers/volumes were absent, no resolver pipe or default WSL server remained, and both private Windows and WSL GUI roots were removed. The original 23 desktop PIDs, original Code executable/product hashes and existing system Gridstator agent PID 618566/unit SHA were preserved. No WSL or Docker restart, global service change, broad Code kill or global shared-storage reset was performed. Credentials and server connection state were removed; only public evidence is retained here.
